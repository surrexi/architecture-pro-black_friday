# Задание 8. Выявление и устранение «горячих» шардов

**Контекст.** В коллекции `products` категория «Электроника» генерирует ~70% запросов, что привело к перегрузке одного
из шардов. Нужна стратегия: как **выявлять** горячие шарды, **устранять** дисбаланс и какие **метрики** мониторить,
чтобы предотвращать повторение.

---

## Цели

1. Оперативно обнаруживать диспропорции нагрузки/данных по шардам.
2. Уметь быстро перераспределять данные (чанки) и/или изменять стратегию шардирования.
3. Встроить наблюдаемость (метрики/алерты) для превентивного реагирования.

---

## Метрики для мониторинга

### A. Состояние шардов и балансировщика

- **Статус шардирования и балансировщика:**
    - `sh.status()` / `db.adminCommand({ balancerStatus: 1 })`
    - `sh.getBalancerState()`, `sh.isBalancerRunning()`
- **Распределение чанков по шардам (на весь кластер и по конкретной коллекции):**
  ```js
  // по всему кластеру
  use config
  db.chunks.aggregate([
    { $group: { _id: "$shard", chunks: { $sum: 1 } } },
    { $sort: { chunks: -1 } }
  ])

  // только для products
  db.chunks.aggregate([
    { $match: { ns: "shop.products" } },
    { $group: { _id: "$shard", chunks: { $sum: 1 } } },
    { $sort: { chunks: -1 } }
  ])
  ```
- **Активность миграций:**
    - `db.currentOp({ desc: "chunk migration" })`
    - Логи балансировщика (поиск `balancer` в журналах mongos/mongod).

### B. Нагрузка на шард (ops/сек и задержки)

- **Операции на каждом шарде/реплике:** `serverStatus().opcounters`, `opcountersRepl` (read/write/delete/update).
- **Время ожидания и очереди:** `network`, `transport`, `connections.available`, `globalLock.currentQueue`.
- **Репликация:** отставание вторичных (`replSetGetStatus` → `members.optime`/`optimeDate`).

### C. Диск/память и WiredTiger

- **WiredTiger cache:** used %, dirty %, eviction stats (`wiredTiger.cache.*`).
- **I/O диска:** `wt transaction checkpoints`, `background flush`, системные метрики диска/FS.
- **Размер коллекции/индексов:** `db.stats()`, `db.products.stats()` (оценка веса).

### D. Метрики уровня приложения (реально важные)

- **QPS/latency по категориям** (label `category`) на уровне API/бизнес-логики.
- **Процент fan-out запросов** (сколько запросов scatter-gather) — по логам/трейсингу.
- **Rate успешных/медленных запросов** по категориям (p95/p99 latency).

> Рекомендация: собирать всё выше через Prometheus (mongodb_exporter) + Grafana. Слои: mongos, mongod(
> primary/secondary), приложение.

## Механизмы устранения дисбаланса (для MongoDB)

### 1) Краткосрочные меры (без изменения ключа)

- **Принудительное дробление и миграция чанков «горячей» категории:**
    - Для шард-ключа `category` (даже hashed) можно *сделать больше чанков* и *распылить* их по разным шардам.
  ```js
  // включить балансировку, если была выключена
  sh.setBalancerState(true)
  // Разбиваем «горячие» чанки (пример: split по найденному документу)
  sh.splitFind("shop.products", { category: "electronics" })
  // Перемещаем один из чанков на другой шард
  sh.moveChunk("shop.products", { category: "electronics" }, "shard02")
  ```
  > Примечание: для hashed-ключа реальные границы чанков — по *хэшированным* значениям. `splitFind` упрощает: указываем
  документ из нужного чанка.
- **Уточнить/уменьшить размер чанка** для более мелкозернистых миграций (по умолчанию ~128MB):
  ```js
  use config
  db.settings.updateOne(
    { _id: "chunksize" },
    { $set: { value: 64 } }, // 64MB
    { upsert: true }
  )
  ```
- **Тюнинг балансировщика:**
  ```js
  sh.startBalancer()                 // явный запуск
  sh.isBalancerRunning()             // проверка
  sh.disableBalancing("shop.products")  // точечно (если нужно перед операциями)
  sh.enableBalancing("shop.products")
  ```
- **Добавить мощности**: временно увеличить `migrationConcurrency`, масштабировать узел (CPU/IO).

### 2) Среднесрочные меры (уточнение ключа)

- **Refine Shard Key** (MongoDB 4.4+) — добавляем поле для лучшего распределения внутри «горячей» категории:
    - Было: `products` → ключ `{ category: "hashed" }`
    - Станет: **составной ключ** `{ category: 1, _id: "hashed" }`
  ```js
  sh.refineCollectionShardKey(
    "shop.products",
    { category: 1, _id: "hashed" }
  )
  ```
  *Эффект:* запросы по категории всё ещё таргетируют подмножество шардов, **но** внутри категории документы теперь
  разносятся по множеству чанков (по `_id`), что убирает «горячую» точку.
- **Zone Sharding (тэгирование шардов)** — выделить shard-пул для горячих категорий:
  ```js
  // назначить зону шардy
  sh.addShardToZone("shard02", "hot-zone")
  // задать диапазон зоны (по первому полю ключа — category)
  sh.updateZoneKeyRange(
    "shop.products",
    { category: "electronics" },
    { category: "electronics" },
    "hot-zone"
  )
  ```
  *Эффект:* нагрузка от «электроники» пойдёт на определённые шарды (можно выделить несколько и масштабировать их
  отдельно).

### 3) Долгосрочные меры (смена стратегии)

- **Resharding** (MongoDB 5.0+): полная смена ключа без простоя (онлайн-процесс).
    - Пример: перейти с `{ category: "hashed" }` на `{ _id: "hashed" }` при доминировании точечных доступов по SKU.
  ```js
  db.adminCommand({
    reshardCollection: "shop.products",
    key: { _id: "hashed" },
    numInitialChunks: 256
  })
  ```
- **Добавление шардов** и переразбивка: горизонтальное масштабирование при росте данных/нагрузки.
- **Кэширование и денормализация в приложении**: CDN/Redis для горячих страниц категории, материализация агрегатов.

## Как выявлять «горячие» шарды

1. **Несоответствие чанков и данных:**
    - Если у `shop.products` слишком много чанков на одном шарде → кандидат на балансировку/миграции.
2. **Перекос QPS/latency/CPU/IO на одном шарде:**
    - Сравниваем `opcounters`, p95/99 latency, CPU/IO между шардами.
3. **Репликация «задыхается»:**
    - Вторичные постоянно отстают на перегруженном шарде.
4. **Фан-аут запросов и повышенный scatter-gather:**
    - На уровне API/логов видно, что большая доля запросов к одной категории бьёт постоянно одни и те же узлы.
5. **Профайлер MongoDB (выборочно):**
    - Включить на «проблемной» БД выборочно и выгрузить топ-коллекции/категории по времени.

## Канонический план действий для кейса «Электроника»

1. **Диагностика (15–30 мин):**
    - Посчитать чанки по `shop.products`, сверить QPS/latency по шардам.
    - Проверить `balancerStatus` и текущее число миграций/ошибок.
2. **Быстрые меры:**
    - `splitFind` + `moveChunk` для документов категории «electronics» на несколько шардов.
    - При необходимости уменьшить `chunksize` до 64MB и запустить/подождать балансировщик.
3. **Структурное решение:**
    - `refineCollectionShardKey("shop.products", { category: 1, _id: "hashed" })`.
    - (Опционально) zone sharding: выделить пул шардов под «горячие» категории.
4. **Профилактика:**
    - Ввести дашборды и алерты (границы по перекосам QPS/latency и по распределению чанков).
    - В приложении — кэширование популярной категории, rate limiting по дешёвым листингам, пагинация.

## Алерты (примеры порогов)

- **Chunk skew:** разница > 25–30% в количестве чанков по шардам для одной коллекции.
- **QPS skew:** один шард обслуживает > 50–60% запросов на пространстве коллекции.
- **Latency:** p95 > целевого SLA на конкретном шарде в 2× относительно медианы по кластеру.
- **Replication lag:** отставание SECONDARY > N секунд устойчиво.
- **WT cache pressure:** used > 90% длительно, рост eviction fail.
