# Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

**Контекст:** у интернет-магазина была проблема с MongoDB: при добавлении новых шардов во время «чёрной пятницы» система
сильно замедлялась из-за перераспределения данных. Решено перейти на Cassandra, где:

- нет лидеров (leaderless-репликация),
- данные распределяются равномерно по кластеру,
- добавление нод не требует полного перераспределения.

---

## 1. Действия пользователей в «чёрную пятницу»

- **Массовые логины** → значительный рост числа сессий.
- **Интенсивные просмотры каталога**: карточки, описания, фильтры по категориям; цены в период акции обычно
  фиксированные.
- **Активная работа с корзинами**: добавления, удаления, слияния гостевых и пользовательских корзин.
- **Оформление заказов**: меньше по числу, чем просмотров, но критично корректно учитывать остатки товаров.
- **Изменение статусов заказов**: выполняется менеджерами или автоматически, не в реальном времени.
- **Просмотр истории заказов**: может немного отставать, что приемлемо для пользователя.

---

## 2. Сущности, переносимые в Cassandra, и их первичные ключи

### 2.1 `sessions` — пользовательские сессии

- **Назначение:** аутентификация, хранение активных сессий с коротким TTL.
- **Первичный ключ:** `PRIMARY KEY (session_id)`
    - **Partition key:** `session_id` (высокая кардинальность, равномерное распределение).
- **Почему Cassandra:** высокий QPS, короткая жизнь записей, eventual consistency приемлема.

**Пример CQL**

```sql
CREATE TABLE sessions
(
    session_id TEXT PRIMARY KEY,
    user_id    UUID,
    created_at TIMESTAMP,
    expires_at TIMESTAMP
) WITH default_time_to_live = 86400; -- 1 день
```

---

### 2.2 `carts` — рабочие корзины

- **Назначение:** быстрые point-lookup/обновления текущей корзины, очистка по TTL.
- **Первичный ключ:** `PRIMARY KEY (cart_id)`
    - **Partition key:** `cart_id` (UUID; равномерно по кольцу).
- **Почему Cassandra:** частые обновления и чтения, TTL; критические проверки выполняются перед чекаутом в строгой БД.

**Пример CQL**

```sql
CREATE TABLE carts
(
    cart_id    UUID PRIMARY KEY,
    user_id    UUID,
    session_id TEXT,
    items      MAP<TEXT,INT>,            -- product_id -> qty
    status     TEXT, -- active | ordered | abandoned
    updated_at TIMESTAMP
) WITH default_time_to_live = 604800; -- 7 дней
```

---

### 2.3 `order_history_by_user` — история заказов (read-модель)

- **Назначение:** быстрый вывод «мои заказы» в UI; наполняется из источника истины (CDC/стрим).
- **Первичный ключ:** `PRIMARY KEY ((user_id), created_at, order_id)`
    - **Partition key:** `user_id`
    - **Clustering keys:** `created_at DESC, order_id`.
- **Почему Cassandra:** append-only, высокий QPS на чтение; допустимо небольшое отставание.
- **Риск горячих партиций:** крайне активные пользователи → решается бакетированием (`user_id#yyyyMM`).

**Пример CQL**

```sql
CREATE TABLE order_history_by_user
(
    user_id    UUID,
    created_at TIMESTAMP,
    order_id   TIMEUUID,
    amount     DECIMAL,
    status     TEXT,
    PRIMARY KEY ((user_id),
    created_at,
    order_id
) ) WITH CLUSTERING ORDER BY (created_at DESC);
```

---

### 2.4 *(Опционально)* `product_catalog_by_category` — выдача каталога для чтения

- **Назначение:** быстрые листинги по категории/цене; **без** остатков и «живых» цен.
- **Первичный ключ:** `PRIMARY KEY ((category_bucket), price, product_id)`
    - **Partition key:** `category_bucket` = `category + '#' + bucket`.
    - **Clustering keys:** `price ASC, product_id`.
- **Почему Cassandra:** высокий QPS на чтение, eventual consistency допустима; бакеты рассеивают нагрузку.

**Пример CQL**

```sql
CREATE TABLE product_catalog_by_category
(
    category_bucket TEXT, -- e.g. "electronics#2"
    price           DECIMAL,
    product_id      TEXT,
    name            TEXT,
    attrs           MAP<TEXT,
    TEXT>,
    PRIMARY KEY ((category_bucket),
    price,
    product_id
) ) WITH CLUSTERING ORDER BY (price ASC);
```

## 3. Обоснование выбора сущностей и ключей

- **Сессии (`sessions`)**: TTL, `session_id` обеспечивает равномерное распределение и отсутствие горячих партиций.
- **Корзины (`carts`)**: быстрые R/W, TTL, финальная валидация в строгой БД.
- **История заказов (`order_history_by_user`)**: read-модель, лаг допустим; `user_id` как PK даёт таргетированные
  запросы. Проблема «суперпользователей» решается бакетами.
- **Каталог (опц.)**: бакетированный PK предотвращает перегруз популярных категорий.

---

## 4. Как модель защищает от «горячих» партиций и проблем решардинга

- **UUID/session_id** → равномерное распределение.
- **Бакетирование** для категорий и активных пользователей → балансировка нагрузки.
- **Append-only схемы** → дешёвая запись и предсказуемое чтение.
- **Решардинг** в Cassandra переносит только часть диапазонов, а не все данные (в отличие от MongoDB).

---

## 5. Стратегии обеспечения целостности данных

- **Hinted Handoff**
    - Для: `sessions`, `carts`.
    - Краткоживущие данные, важна низкая задержка.

- **Read Repair**
    - Для: `order_history_by_user`, опционально для `product_catalog`.
    - Часто читаемые таблицы, удобно подлечивать реплики при чтении.

- **Anti-Entropy Repair**
    - Для всех таблиц.
    - Необходима регулярная синхронизация, особенно в мульти-DC.

### Компромисс latency ↔ консистентность

- **Sessions/carts:** приоритет скорости → упор на Hinted Handoff.
- **История заказов:** важна согласованность «в итоге» → Read Repair + Anti-Entropy.
- **Каталог:** eventual consistency допустима, но Repair нужен для долгосрочной целостности.

---

## Итог

- В Cassandra целесообразно переносить: **sessions, carts, order_history_by_user** и при необходимости
  **product_catalog_read**.
- **Inventory, orders (агрегат), payments** оставляем в строгой БД.
- Модель обеспечивает равномерное распределение, устойчивость к горячим партициям и масштабируемость под «чёрную
  пятницу».
- Целостность поддерживается стратегиями Hinted Handoff, Read Repair и Anti-Entropy в зависимости от сущности.
